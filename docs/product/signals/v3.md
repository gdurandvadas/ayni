# Historical Signal Schema v3 (`0.3.0`)

Schema v3 was emitted with the exact schema string `0.3.0`. It added explicit
completion accounting and finding identity to the v2 run envelope. This page is
a historical reference only: current Ayni uses [schema v4](v4.md) and does not
parse, produce, migrate, or compare v3 artifacts.

For the stable signal vocabulary, see the [signal index](../signals.md). Schema
v3's implementation authority is the `0.3.0` contract in `core/src/signal.rs`,
`core/src/finding.rs`, and `core/src/comparison.rs` before v4 was published.

## Serialized envelope

The v3 `RunArtifact` serialized this flat top-level object:

| Field | JSON type | Historical rule |
| --- | --- | --- |
| `schema_version` | string | Present and accepted only as `0.3.0` by the then-current core. |
| `generated_at` | string | Present. |
| `ayni_version` | string | Present. |
| `invocation` | object | `command`, `languages`, and optional `scope`. |
| `output` | object | `format` and `destination`. |
| `config_path` | string | Present. |
| `repository_root` | string | Present. |
| `completion` | object | Completion scope, state, counts, and issues. |
| `aggregate` | object | Canonical derived summary. |
| `applied_thresholds` | array | Canonical row-order threshold projection. |
| `rows` | array | Signal rows. |
| `offender_summaries` | array | Canonical row-order offender summaries. |
| `failure_summaries` | array | Omitted when no command failure occurred. |

V3 did not serialize execution mode, a policy digest, an environment-lock
fingerprint, a source fingerprint, or tool versions. Those fields required the
new v4 envelope rather than an in-place change to `0.3.0`.

Language values were `rust`, `go`, `node`, `python`, and `kotlin`. A scope had
required `workspace_root` and optional `path`, `package`, and `file` strings.

## Completion

`completion.scope` was `repository` or `requested`; requested evidence could
not establish repository completion. `completion.state` was `complete` or
`incomplete`. The object also contained u64 `expected_targets`,
`detected_targets`, `completed_targets`, and `skipped_targets`, plus ordered
`issues`.

Each issue contained `language`, `configured_root`, `stage`, and `message`.
`stage` was `detection`, `resolution`, `selection`, `scheduling`, or
`collection`. Counts had to satisfy:

- `detected_targets <= expected_targets`;
- `completed_targets <= detected_targets`;
- `skipped_targets == expected_targets - completed_targets`;
- detection issues equaled expected minus detected targets; and
- total issues equaled skipped targets.

A complete artifact had no skipped targets or issues; an incomplete artifact
had at least one of each. Row completion keys `(language, configured root,
kind)` had to be unique. A complete repository artifact represented exactly its
completed targets, each with the same non-empty kind set.

## Derived views

`aggregate` contained `status`, `total_rows`, `passing_rows`, `failing_rows`,
`warning_offenders`, and `failing_offenders`. Status passed only for complete
evidence whose rows all passed. Test offenders counted as failures; other
offenders used `level`.

Each `applied_thresholds` entry copied `kind`, `language`, `scope`, and `budget`
from its row. Each non-empty `offender_summaries` entry contained `kind`,
`language`, `scope`, `total`, `warning_count`, and `failing_count`. Each
`failure_summaries` entry contained `kind`, `language`, `scope`, `category`,
`classification`, `command`, `cwd`, optional `exit_code`, and `message`.

The v3 deserializer re-derived all four views and rejected a mismatch.

## Rows and payloads

Every row had `kind`, `language`, `scope`, `pass`, internally tagged `result`,
internally tagged `budget`, and tagged `offenders`. There was no
`delta_vs_previous` field.

The historical `Budget` variants carried arbitrary JSON values. Normal Ayni
producers emitted the shapes below, but v3 core did not close those shapes or
require the row, result, budget, and offender kind tags to align during ordinary
artifact serialization. V4 added those fail-closed guarantees.

| Kind | Result fields | Produced budget fields | Offender payload fields |
| --- | --- | --- | --- |
| `test` | `total_tests`, `passed`, `failed`, optional `duration_ms`, `runner`, optional `failure` | empty object | optional `file`, optional `line`, `message`, optional `test_name` |
| `coverage` | optional `percent`, `line_percent`, `branch_percent`, `engine`, `status`, optional `failure` | optional line/branch warn/fail percentages | `file`, optional `line`, `value`, `level` |
| `size` | `max_lines`, `total_files`, `warn_count`, `fail_count`, optional `failure` | normally `rules` entries; focused/failure paths could use `warn`/`fail` or empty | `file`, `value`, `warn`, `fail`, `level` |
| `complexity` | `engine`, `method`, `measured_functions`, `max_fn_cyclomatic`, optional `max_fn_cognitive`, `warn_count`, `fail_count`, optional `failure` | optional `fn_cyclomatic` and `fn_cognitive` warn/fail objects | `file`, `line`, `function`, `cyclomatic`, optional `cognitive`, `level` |
| `deps` | `crate_count`, `edge_count`, `violation_count`, optional `failure` | optional `forbidden` pattern map | `from`, `to`, `rule`, `level` |
| `mutation` | `engine`, `killed`, `survived`, `timeout`, optional `score`, optional `failure` | optional `enabled` | optional `file`, optional `line`, `mutation_kind`, `message`, `level` |

`level` was `warn` or `fail`. A command `failure` contained `category`,
`classification`, `command`, `cwd`, optional `exit_code`, and `message`.

## Historical finding encoding

The normal v3 CLI materialized each offender as a flat finding by adding:

```json
{
  "id": "ayni:finding:v1:sha256:<64 lowercase hex characters>",
  "verification": {
    "command": "ayni verify size --config './.ayni.toml' --language rust --root '.' --file 'src/lib.rs'"
  }
}
```

The identity used a versioned, length-prefixed SHA-256 input based on language,
kind, and stable offender semantics. Severity, thresholds, current measured
values, ordering, checkout location, timestamps, and command text were excluded.
Exact duplicates were removed before IDs were assigned.

However, v3 core serialization fell back to raw offenders when its separate
in-memory finding vector was absent. Deserialization accepted either finding
encoding or legacy raw encoding for all non-empty rows and rejected only a mix
of the two. It also did not verify finding-vector length or same-kind payload
equality during ordinary serialization. These historical acceptance rules are
recorded here so consumers do not infer v4 guarantees from a v3 document.

## Historical comparison

The v3 comparison document used comparison schema `0.1.0`. Both artifacts had
to be complete and use `0.3.0`. Rows matched by `kind`, `language`, and optional
relative `scope.path`, `scope.package`, and `scope.file`. The result contained
sorted `matched`, `changed`, `added`, and `removed` collections; row changes
tracked `pass`, typed numeric result metrics, and finding-ID additions/removals.

Because v3 carried no portable execution provenance, comparison could not prove
that two artifacts used the same policy, environment, or tools. It ignored
timestamps, roots, output metadata, budgets, tool labels, offender presentation,
verification commands, and finding order. V4 requires compatible locked
provenance and rejects host evidence.

## Compatibility

Current Ayni accepts only `0.4.0` run artifacts. It does not treat this v3 page
as a migration promise, and `ayni results compare` does not accept a v3 input.
