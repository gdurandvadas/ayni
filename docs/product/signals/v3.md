# Signal Schema v3 (`0.3.0`)

The current serialized schema string is `0.3.0`. Schema v3 defines explicit,
fail-closed completion evidence, closed row/budget validation, and portable run
provenance. It is not wire-compatible
with [historical schema v2](v2.md), and Ayni does not automatically convert v2
artifacts.

Source authority is `core/src/signal.rs` for `AYNI_SIGNAL_SCHEMA_VERSION`,
`RunArtifactSerialization`, `RunArtifactWire`, `RunCompletion`, and the row and
payload types, `core/src/finding.rs` for finding identity, metadata,
deduplication, and serialization, and `core/src/comparison.rs` for explicit
artifact comparison. For signal meanings and the closed vocabulary, see the
[signal-contract index](../signals.md).

## Serialized envelope

`RunArtifact` serializes a flat top-level envelope; its internal `metadata`
field is not nested in JSON.

| Field | JSON type | Serialization rule |
| --- | --- | --- |
| `schema_version` | string | Present and exactly `0.3.0` when deserialized by the current core contract. |
| `generated_at` | string | Present. |
| `ayni_version` | string | Present. |
| `invocation` | object | Present; `command` (string), `languages` (array of language values), and optional `scope`. |
| `output` | object | Present; `format` and `destination` strings. |
| `config_path` | string | Present. |
| `repository_root` | string | Present. |
| `execution_mode` | `managed` \| `host` | Present. Managed and host evidence are provenance-incompatible. |
| `contract_digest` | string | Present lowercase `sha256:<64 hex>` digest of the exact policy bytes used by the run. |
| `environment_lock_fingerprint` | string | Required for managed evidence and forbidden for host evidence; identifies the validated lock used for execution. |
| `source_fingerprint` | string | Present lowercase SHA-256 fingerprint of the measured source snapshot, excluding generated runtime/build state. |
| `tool_versions` | array | Present, sorted, unique `{ tool, version }` records. Managed evidence includes the locked Mise, runtime, package-manager, repository-tool, and signal-tool versions relevant to the run; host evidence may be empty because its tools are not locked. |
| `completion` | object | Present; completion scope, state, reconciled target counts, and ordered issues. |
| `aggregate` | object | Present derived summary. Its status cannot pass when completion is incomplete. |
| `applied_thresholds` | array | Present derived row summary. |
| `rows` | array of signal rows | Present. |
| `offender_summaries` | array | Present derived row summary. |
| `failure_summaries` | array | Omitted when no command failures occur. |

Language values are `rust`, `go`, `node`, `python`, and `kotlin`. A row scope
has required `workspace_root` and optional `path`, `package`, and `file` strings.

## Completion contract

`completion` has this shape:

| Field | JSON type | Contract |
| --- | --- | --- |
| `scope` | `repository` \| `requested` | `repository` represents the configured repository contract; `requested` represents only an explicit focused request. Requested evidence must not be treated as repository completion. |
| `state` | `complete` \| `incomplete` | `complete` means every expected target emitted every requested signal row, even when a row failed. `incomplete` means at least one target did not emit that full row set. |
| `expected_targets` | u64 | Number of configured language/root targets after valid command selection. |
| `detected_targets` | u64 | Expected targets detected by their owning adapters. |
| `completed_targets` | u64 | Targets that emitted every requested row. Row pass/fail does not affect this count. |
| `skipped_targets` | u64 | Exactly `expected_targets - completed_targets`. |
| `issues` | array | One ordered structured issue for each skipped target. |

Each issue contains `language`, `configured_root`, `stage`, and `message`.
`stage` is one of `detection`, `resolution`, `selection`, `scheduling`, or
`collection`. Detection issues exactly account for
`expected_targets - detected_targets`; all remaining issues account for
detected targets that did not complete. Consequently, `issues.length` equals
`skipped_targets`.

A `complete` artifact has no skipped targets or issues. An `incomplete`
artifact has at least one skipped target and issue. Deserialization rejects
counts, issues, or state that do not reconcile.

Completion is about row-set production, not check success. A target whose tool
produced all requested typed rows is completed even if those rows fail. A
completed target must emit every requested row; omitted rows cannot be treated
as passing or completed work.

Completion is row-aware. Core requires unique `(language, configured root,
signal kind)` row keys and structurally derives which targets and signal-kind
sets are represented by the wire rows; it rejects completion counts that cannot
reconcile with those rows. For a complete repository artifact, represented
targets must have the same non-empty signal-kind set. This is deliberately a
structural wire check, not proof that the rows match a particular policy: the
expected target/row plan is in-process planning evidence and is not serialized.
Consumers must therefore use the reconciled completion state and issues, not
attempt to reconstruct a policy plan from an artifact alone.

## Aggregate and derived summaries

`aggregate` contains `status` (`pass` or `fail`), `total_rows`, `passing_rows`,
`failing_rows`, `warning_offenders`, and `failing_offenders` (all counts are
u64). Status is `pass` only when completion is `complete` and every emitted row
passes. Therefore an incomplete artifact, including one with no rows, always
aggregates to `fail`.

`applied_thresholds`, `offender_summaries`, and `failure_summaries` are derived
in row order as documented for [schema v2](v2.md). On input, core rebuilds all
four derived views (`aggregate` included) and rejects a mismatch.

## Rows and payloads

Each `rows` item has `kind`, `language`, `scope`, `pass`, `result`, `budget`, and
`offenders`. `result` and `budget` are internally tagged with `kind`;
`offenders` is `{ "kind": <kind>, "items": [...] }`. The row's four kind values
must agree. Schema-v3 rows never contain an implicit historical delta;
comparison is a separate explicit model.

“Optional” below means the field is omitted when null.

### `test`

| Object | Fields |
| --- | --- |
| `result` | `total_tests` (u64), `passed` (u64), `failed` (u64), `duration_ms` (optional u64), `runner` (string), `failure` (optional command failure) |
| `budget` | Empty typed object; test policy has no numeric threshold. |
| `offenders.items[]` | `file` (optional string), `line` (optional u64), `message` (string), `test_name` (optional string) |

### `coverage`

| Object | Fields |
| --- | --- |
| `result` | `percent` (optional f64), `line_percent` (optional f64), `branch_percent` (optional f64), `engine` (string), `status` (string), `failure` (optional command failure) |
| `budget` | Optional numeric `line_percent_warn`, `line_percent_fail`, `branch_percent_warn`, and `branch_percent_fail`; unknown fields are rejected. |
| `offenders.items[]` | `file` (string), `line` (optional u64), `value` (f64), `level` (`warn` \| `fail`) |

`percent` is the primary headline percentage from 0 through 100. Headline
selection prefers `percent`, then `line_percent`, then `branch_percent`.

### `size`

| Object | Fields |
| --- | --- |
| `result` | `max_lines` (u64), `total_files` (u64), `warn_count` (u64), `fail_count` (u64), `failure` (optional command failure) |
| `budget` | `rules` array of `{ glob, warn, fail }`; empty failure-path budgets and legacy focused `warn`/`fail` pairs are accepted, but unknown fields are rejected. |
| `offenders.items[]` | `file` (string), `value` (u64), `warn` (u64), `fail` (u64), `level` (`warn` \| `fail`) |

### `complexity`

| Object | Fields |
| --- | --- |
| `result` | `engine` (string), `method` (string), `measured_functions` (u64), `max_fn_cyclomatic` (f64), `max_fn_cognitive` (optional f64), `warn_count` (u64), `fail_count` (u64), `failure` (optional command failure) |
| `budget` | Optional `fn_cyclomatic` and `fn_cognitive` objects, each with numeric `warn` and `fail`; unknown fields are rejected. |
| `offenders.items[]` | `file` (string), `line` (u64), `function` (string), `cyclomatic` (f64), `cognitive` (optional f64), `level` (`warn` \| `fail`) |

### `deps`

| Object | Fields |
| --- | --- |
| `result` | `crate_count` (u64), `edge_count` (u64), `violation_count` (u64), `failure` (optional command failure) |
| `budget` | Optional `forbidden` map from source patterns to destination-pattern arrays; unknown fields are rejected. |
| `offenders.items[]` | `from` (string), `to` (string), `rule` (string), `level` (`warn` \| `fail`) |

### `mutation`

| Object | Fields |
| --- | --- |
| `result` | `engine` (string), `killed` (u64), `survived` (u64), `timeout` (u64), `score` (optional f64), `failure` (optional command failure) |
| `budget` | Optional boolean `enabled`; unknown fields are rejected. |
| `offenders.items[]` | `file` (optional string), `line` (optional u64), `mutation_kind` (string), `message` (string), `level` (`warn` \| `fail`) |

Each optional result `failure` contains `category`, `classification`, `command`,
`cwd`, optional `exit_code`, and `message`. Budgets are signal-tagged applied
policy payloads and are repeated in the derived `applied_thresholds` view.

For every enabled adapter, a successful test command that discovers zero tests
produces a failing test row with `result.total_tests` preserved as `0` and an
actionable test offender. This is a verification finding, not a command failure:
`result.failure` remains absent unless the external command itself failed.

### Finding identity and verification metadata

Every serialized offender is a flat finding: it retains its historical offender
fields and adds an `id` and a copyable verification command. Adapter-owned typed
targets are an internal mapping contract and never appear on the v3 wire.

The staged shape is:

```json
{
  "id": "ayni:finding:v1:sha256:<64 lowercase hex characters>",
  "verification": { "command": "ayni verify size --config './.ayni.toml' --language rust --root '.' --file 'src/lib.rs'" },
  "file": "src/lib.rs",
  "value": 800,
  "warn": 400,
  "fail": 700,
  "level": "fail"
}
```

`id` and `verification` are flattened alongside the existing offender fields;
there is no nested `offender` object. The CLI revalidates every adapter target
against its declared selector support, then renders `ayni verify <signal>` with
the originating artifact config path, an explicit `--language`, and the row's
exact normalized configured `--root` (`.` for the repository root). Config,
root, and selector values are POSIX-shell single quoted; an
embedded single quote is represented by closing, emitting a double-quoted
single quote, and reopening the single-quoted argument, so hostile paths,
package names, and test names remain copyable as one argument. The narrowest
supported file, package, and/or test-name target is used; synthetic zero-test
findings receive an unscoped or already-scoped actionable command.

Identity input is a versioned, length-prefixed canonical representation of the
row language, signal kind, and stable semantic offender fields:

- test: relative file, line, and test name; message only when all three are
  absent (including the synthetic zero-test finding);
- coverage: relative file and optional line;
- size: relative file;
- complexity: relative file, line, and function name;
- deps: source, destination, and rule;
- mutation: relative file, line, mutation kind, and message.

Paths are lexical, slash-normalized, and made relative to the supplied checkout
root. Severity, thresholds, measured values, output order, checkout root,
timestamps, and verification target are excluded. Exact canonical duplicates
are removed before IDs are assigned, retaining their first output position.
The complete canonical bytes are hashed with SHA-256 and the full digest is
serialized as `ayni:finding:v1:sha256:<digest>`; digests are never truncated.
An otherwise impossible digest collision between different canonical inputs is
a deterministic, fail-closed construction error rather than an order-based
suffix.

The ID identifies the finding's stable semantics, not its current severity,
measurement, ordering, checkout location, or generated command. Consumers may
use it to correlate the same finding across complete artifacts. The
`verification.command` is instead an exact, copyable command for the current
adapter-declared target; consumers must not synthesize or modify selectors.

## Explicit artifact comparison

Core compares two artifacts with comparison schema `0.1.0`. Both inputs must be
valid, complete schema-v3 artifacts. An incomplete artifact, a non-`0.3.0`
artifact, malformed completion or summary data, duplicate row key, mismatched
typed row payload, missing finding ID, invalid relative matching path, or
non-finite metric is rejected. V2 artifacts are not converted.

The public entry point is `ayni results compare --baseline <artifact>
--candidate <artifact> [--output human|json]`. It reads exactly the two named
files and does not discover a repository, inspect Git, load an implicit prior
artifact, fetch or store history, or write output. The default human report and
the JSON report are projections of the same typed comparison model. JSON is one
deterministic document on stdout; diagnostics are written to stderr and no
partial JSON is emitted on failure. A valid comparison exits zero even when it
contains added, removed, or changed rows.

Before matching rows, comparison requires compatible provenance: identical
`execution_mode`, `contract_digest`, `environment_lock_fingerprint`, and
`tool_versions`. This rejects host-versus-managed comparisons, policy drift,
and changes to the locked measurement environment. `source_fingerprint` is
intentionally allowed to differ because comparison exists to evaluate different
source states.

Rows then match by `kind`, `language`, and the optional relative `scope.path`,
`scope.package`, and `scope.file`. `scope.workspace_root`, top-level
`repository_root`, artifact file location, timestamps, invocation output mode,
and repository or Git state do not participate. Core performs no Git or branch
discovery.

The deterministic comparison contains `comparison_schema_version`,
`artifact_schema_version`, and sorted `matched`, `changed`, `added`, and
`removed` collections. `changed` contains the keys of changed matches. Every
matched row has a `changed` boolean and a typed `changes` object containing only
differences in:

- `pass`, as a typed `before`/`after` boolean pair;
- numeric result metrics, ordered by metric name with typed integer or float
  values (and optional values when a metric exists on only one side); and
- finding IDs, as ordered `added` and `removed` ID sets.

After provenance compatibility succeeds, changes to presentation metadata, tool
labels, offender presentation, verification commands, or finding order do not
make a matched row changed.

## Compatibility and failure behavior

Consumers must select this contract only when `schema_version` is `0.3.0`.
Current core deserialization rejects another version, a missing completion
object, unreconciled completion accounting, or a non-canonical derived summary.
There is no v2 fallback or migration payload.

Terminal and Markdown reports display completion scope and state separately
from row pass counts. Structured completion issues identify targets that did
not finish; command failures remain typed row failures and do not by themselves
make completion incomplete when the requested row set was emitted.
